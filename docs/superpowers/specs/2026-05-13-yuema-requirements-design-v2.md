# 约麻小程序需求说明设计书（V2.0 · 实现对齐版）

**文档版本**：V2.0  
**编制日期**：2026-05-13  
**文档性质**：在《约麻小程序开发需求设计书》（V1.1，2026-05-05）与当前仓库实现之间做**差距分析、验收口径闭合与路线规划**；替代「仅 PRD」作为迭代排期与联调的**单一事实来源（SSOT）**。  
**基线代码**：`yuema-miniprogram`、`yuema-server`；数据库脚本 `yuema-server/sql/init.sql`。  
**上游引用**：根目录 `约麻小程序开发需求设计书.md`；`docs/功能需求-对齐说明.md`；`docs/superpowers/specs/2026-05-12-frontend-optimization-design.md`（性能与全局状态，不改变业务需求边界）。

## 1. 文档目标与适用范围

| 目标 | 说明 |
|------|------|
| 对齐实现 | 将 PRD 中的 Epic/Story 映射为**可验收**条目，并标明与真实路由、页面、库表的一致性。 |
| 暴露差距 | 明确「PRD 要求但代码未满足」「代码已有但 PRD 未写」「行业/平台额外要求」三类差距。 |
| 闭合决策 | 对影响验收写法的开放项给出**可选方案**与推荐默认，便于产品二选一后冻结验收。 |
| 规划里程碑 | 划分 MVP 收口、合规专项、P1 能力、B 端独立交付，避免范围蔓延。 |

**不在本文展开**：商家端独立应用的详细 Story（仍标记为仓库外）；具体 UI 像素级规范（沿用 V1.1 §6 与现有小程序风格）。

## 2. 版本策略与信息架构决议

### 2.1 相对 V1.1 的显式变更

| 主题 | V1.1 描述 | V2.0 决议 |
|------|-----------|-----------|
| 底部 Tab | 5 Tab，中间突出「创建」 | **V1 实现为 4 Tab**（首页 / 牌局 / 场地 / 我的）；创建从首页或牌局流程进入。若未来对齐 5 Tab，单独立 UI Epic。 |
| 场地预订与支付 | P0 | **整体延后至 P1+**（与既有产品决议一致）；`orders` 等库表存在但 C 端预订链路不在 MVP 验收内。 |
| 牌局详情接口名 | `/api/room/detail` | 实现为 **`GET /api/room/info?roomId=`**（`context-path` 为 `/api` 时路径为 `/room/info`）。PRD 与对外文档以实际为准或做别名网关（可选）。 |
| 计分明细 | `/api/score/history` | 实现为 **`GET /api/score/list`**，前端按 `roundNo` 聚合展示。 |
| 记分单条修改 | `PUT /score/update` | 实现为 **改分申请 + 投票**（`modify-request` / `modify-vote` 等），与「需他人确认」语义一致，优于单条静默 update。 |

### 2.2 HTTP / WebSocket 约定

- 下文接口路径均相对于后端 **`/api`**（与 `application.yml` 的 `server.servlet.context-path` 及小程序 `apiBaseUrl` 一致）。  
- WebSocket：**`/api/ws/room`**，鉴权 Query `token`；消息 `type`/`payload` 以服务端与 `RoomWebSocketHandler` 约定验收。

## 3. 差距总览（仍需满足 vs 当前不足）

### 3.1 定义

| 术语 | 含义 |
|------|------|
| **仍需满足** | 相对 V1.1 PRD 或平台/行业**合理默认**，当前未实现或验收不可闭环的能力。 |
| **当前不足** | 已实现但**规则未闭合**、体验缺口、合规缺失、或文档与代码不一致导致联调风险之处。 |

### 3.2 按 Epic 一览

| Epic | 仍需满足（相对 PRD/平台） | 当前不足（实现侧） |
|------|---------------------------|---------------------|
| A 用户系统 | 手机号绑定若走微信规范需 `getPhoneNumber` + 后端换号 + 隐私弹窗；个性签名/擅长玩法若要坚持 PRD 需字段与接口；实名（P1）未规划接口 | 手机号为手动录入；无个性签名；段位仅 `level` 映射名无算法文档 |
| B 牌局 | 缺人自动匹配；开局「人到齐」确认流；聊天语音/表情；链接加入需运营验证分享卡片 | 直接 `start` 无全员确认；仅文字+WS；自动匹配未实现 |
| C 计分 | 账单与底注/台费/货币的**产品规则写死**；删除一局若要坚持「他人确认」需投票模型扩展 | `settlement` 中 `amount` 与分数关系待乘底注等规则闭合；删局为权限删除非全员投票 |
| D 场地 | 地图 Tab、筛选、评价 C 端展示；预订支付（P1+） | 列表/附近有；评价表未接 C 端；预订已延后 |
| E 社交 | 好友、牌友评价、战绩分享（卡片/生图） | 库表有 `friendships`/`user_reviews`，UI 占位；分享未做生图链路 |
| F 商家端 | 全量 B 端 | **未在仓库** |
| G 我的扩展 | 会员、优惠券（P2） | 未开始 |
| H 合规与安全 | 隐私政策与用户同意、敏感接口说明；内容审核策略；涉赌边界话术与功能隔离；实名/防沉迷（若做） | 对齐说明中标记为未开始；需独立里程碑 |

### 3.3 行业与微信生态（联网结论摘要）

以下**非法律意见**，用于产品与技术自查清单：

1. **手机号**：微信侧提供「手机号快速验证」能力；需小程序端 `open-type="getPhoneNumber"`（或组合 `agreePrivacyAuthorization`）、服务端调用 `getuserphonenumber` 换号；主体需符合开放平台类目与认证要求。  
2. **隐私合规**：收集个人信息（昵称、头像、手机号、位置等）需**隐私政策**及用户**明示同意**后再调对应接口（微信隐私接口框架）。隐私政策中应写明收集项、目的、存储期限、共享范围等，并与实际调用一致，否则影响审核。  
3. **棋牌/工具定位**：持续强调「约局工具 + 场地信息」，**不提供积分提现、随机博彩玩法、现金结算撮合**；聊天与 UGC 需配套风控/举报路径以降低审核风险。  
4. **行业常见能力**（对标自助棋牌室 SaaS）：在线预约时段、包间、**微信支付**、订单退款、门店后台、会员营销、评价客服。约麻已将预订支付整体 P1+，与「先做约局+计分」策略一致，但需在对外话术与商业化路径上管理预期。

## 4. 功能需求（可验收表述）

### 4.1 Epic A — 用户系统

| ID | 需求 | 优先级 | 验收状态 | 验收要点 / 缺口处理 |
|----|------|--------|----------|---------------------|
| A1 | 微信登录 | P0 | 已实现 | `POST /user/login`；`NEED_PROFILE` 引导补资料 |
| A2 | 手机号绑定 | P0 | 部分 | **决策点**：维持手动输入（A 方案）或接入微信手机号组件（B 方案）。选型后更新隐私政策与接口文档 |
| A3 | 个人资料 | P0 | 部分 | 昵称/头像/手机可改；**个性签名**未在 `UpdateUserDTO` 则标为 P1 或从 PRD 删除 |
| A4 | 段位系统 | P1 | 部分 | 展示层可验收；若需「雀士→雀圣」算法，需另附《段位规则》小文档 |
| A5 | 实名认证 | P1 | 未开始 | 依赖第三方实名服务；单独立项 |

### 4.2 Epic B — 牌局系统

| ID | 需求 | 优先级 | 验收状态 | 验收要点 / 缺口处理 |
|----|------|--------|----------|---------------------|
| B1 | 创建/加入/离开/踢人/转让 | P0 | 已实现 | 路由见 `docs/功能需求-对齐说明.md` §1.3 |
| B2 | 缺人自动匹配 | P0 | 未实现 | **仍为差距**：需匹配队列规则、超时、通知策略 |
| B3 | 开局确认 | P0 | 未实现 | **仍为差距**：建议「全员按钮确认」或「倒计时自动开」二选一写进 Story |
| B4 | 实时聊天 | P0/P1 | 部分 | 文字+WS 已验收；语音/表情列 P1 |
| B5 | 邀请分享 | P0 | 部分 | 小程序码已有；分享卡片依赖微信后台配置与素材 |

### 4.3 Epic C — 计分系统

| ID | 需求 | 优先级 | 验收状态 | 验收要点 / 缺口处理 |
|----|------|--------|----------|---------------------|
| C1 | 逐局记分 / 汇总 / 明细 | P0 | 已实现 | `record` / `summary` / `list` |
| C2 | 账单结算 | P0 | 部分 | **必须在验收表写死**：底分、台费是否进分摊、货币单位、`amount` 计算公式 |
| C3 | 记分修改需他人确认 | P1 | 已实现 | 改分申请 + 投票 |
| C4 | 删除一局需他人确认 | PRD §5.3 | 部分 | 当前为房主或该局记分人删除；若坚持 PRD，需新增投票删局流 |
| C5 | 战绩分享 | P1 | 未开始 | 决策：仅 `onShareAppMessage`（低）或服务端生图（高） |

### 4.4 Epic D — 场地系统

| ID | 需求 | 优先级 | 验收状态 | 验收要点 / 缺口处理 |
|----|------|--------|----------|---------------------|
| D1 | 列表 / 附近 / 详情 / 包间列表 | P0 | 已实现 | 无在线支付验收 |
| D2 | 地图模式 / 强筛选 | P0 | 部分 | 可标为「增强」；MVP 以列表+LBS 为主 |
| D3 | 用户评价展示 | P0 | 部分 | C 端未接评价表则标为差距或降为 P1 |
| D4 | 预订 / 订单 / 支付 | P0→**P1+** | 已延后 | 与商业化、合规、商家端一并规划 |

### 4.5 Epic E — 社交系统

| ID | 需求 | 优先级 | 验收状态 | 验收要点 / 缺口处理 |
|----|------|--------|----------|---------------------|
| E1 | 好友 | P1 | 库表有，UI 未接 | 需接口联调 + Tab/入口决策 |
| E2 | 牌友评价 | P1 | 库表有，UI 未接 | 评价维度、防刷、展示位置 |
| E3 | 排行榜 / 信誉 | P2 | 未开始 | 依赖数据聚合与反作弊 |
| E4 | 动态分享 | P1 | 部分 | 复用微信分享 + 可选生图 |

### 4.6 Epic F — 商家端

**未在仓库**；V2.0 将 B 端列为**独立产品**或后续仓库，不在本小程序迭代内合并验收。

### 4.7 Epic H — 合规与安全（强制里程碑）

| ID | 需求 | 说明 |
|----|------|------|
| H1 | 用户协议与隐私政策 | 上架必备；与收集项、微信隐私接口调用一致 |
| H2 | 个人信息最小化 | 仅收集业务必要字段；位置说明「用于附近牌局/场地」 |
| H3 | UGC 与聊天 | 敏感词、举报入口、频次限制（按体量分阶段） |
| H4 | 涉赌隔离 | 产品文案与功能边界审查；禁止积分兑换现金、随机匹配赌资等 |
| H5 | 实名 / 防沉迷 | 若目标用户含未成年人场景需专项评估；否则在隐私与注册流程中做年龄提示 |

## 6. 开放问题（需产品冻结后写入验收表）

1. **手机号**：手动输入 vs 微信 `getPhoneNumber`（影响隐私条款、后端接口、审核材料）。  
2. **结算公式**：底分 × 分数？台费固定扣减？`amount` 是否允许非零和校验例外？  
3. **删局规则**：权限删局 vs 全员投票删局。  
4. **开局确认**：不做 / 全员确认 / 自动开 —— 三选一。  
5. **战绩分享**：低方案与高方案取舍。  
6. **地图 Tab**：MVP 不做 / 下一版本做。

## 7. 建议里程碑（供排期）

| 阶段 | 目标 | 主要交付 |
|------|------|----------|
| M0 收口 | P0 可演示、可联调 | 闭合 C2 结算规则文档 + 关键流程无阻塞 Bug |
